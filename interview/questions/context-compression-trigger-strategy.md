# 上下文压缩算法应该在什么条件下触发？

## Variants

- 上下文压缩什么时候触发？
- 如何避免上下文无限膨胀？
- 上下文超长了怎么办？有没有考虑过上下文压缩？
- 压缩过程中丢失工具调用历史导致模型重复调用工具，怎么解决？

## Short Answer

成熟系统通常不是单一触发，而是多重触发策略：token 预算硬阈值、轮次滑窗阈值、任务阶段切换阈值、模型质量预警阈值。核心目标是把压缩从“临界救火”变成“常态治理”，在不牺牲正确性的前提下控制成本与延迟。

## Full Answer

这道题其实是在问你：你有没有在真实系统里被长上下文折磨过。

我踩过几个坑之后总结下来，压缩触发不是配一个阈值就完事，而是三层防线加一个质量护栏。

第一层：token 硬阈值。比如模型窗口 128k，我一般设到 75%-80% 就强制触发压缩。为什么不是 90%？因为你要留 buffer——工具调用返回的 token 量你估不准，万一一个搜索结果塞进来直接超了窗口，请求就挂了。这个阈值还不能写死，不同模型的窗口不一样，Claude Sonnet 和 GPT-4o 你写同一个数就是在给自己埋雷。

第二层：轮次滑窗触发。这个的思路是"远的折叠，近的保留"。比如每 10 轮对话，把前 7 轮压缩成结构化摘要——不是简单缩短文本，而是提取出实体、目标、已完成的步骤、当前约束、待解决问题。这里有一个关键 insight：压缩后的产物不能是一坨自然语言，得是后续 agent 能稳定引用的结构化状态。否则下一轮 agent 又要从自然语言里去猜"我之前到底做了啥"，准确率直接掉。

第三层：阶段触发。这是面试里最容易出彩的点。比如一个 agent 从"资料检索阶段"切到"代码生成阶段"，检索的中间细节——哪些网页看过、哪些搜了没结果——对代码生成来说全是噪声。这时候在状态机流转时主动触发一次压缩，只保留检索的结论和关键证据链接，把过程全扔掉。同样，从代码生成切到汇总阶段时，中间 debug 的试错过程也可以丢掉，只保留最终方案和失败过的路径标记。这就是"不同阶段需要不同粒度的上下文"。

这三层之外还有一个最容易忽略、但也最致命的东西：质量护栏。我吃过最大的亏是什么？压缩把否定条件丢了。比如用户说"不要修改 production 分支"，压缩完变成了"修改分支"，agent 就真的去改了。所以压缩完之后必须做关键信息一致性校验——约束还在不在？用户偏好还在不在？任务 ID 对不对得上？我们线上会保留一个"可回放指针"，万一校验不通过可以回退。而且压缩策略本身也要做回归评测，不能拍脑袋上了就完事。

最后说下监控怎么做。不能只看压缩后省了多少 token——那是成本视角，会把你带偏。你得同时看压缩后任务成功率有没有波动、有没有因为压缩导致回滚。 核心一句话：压缩的目的是省钱，但不能以丢正确性为代价。把这个讲清楚，面试官就知道你是真的在线上跑过。

再补一个很真实的坑：工具调用历史被压缩后，模型会重复调用。

这个问题的根本原因是——模型判断"要不要调某个工具"依赖于上下文里有没有"这个工具已经被调用过，结果是 X"。一旦 tool call 的消息对被压缩掉，模型以为没调过，就会重复调。我们的线上遇到过 embedding 模型反复查同一个文本，白白浪费几千个 token。

解法分三层。第一层，压缩时不简单删掉工具调用历史，而是提炼成摘要注入 System Prompt 或 Memory Block 里——"已完成操作：查询了用户地址（结果：xxx），搜索了附近餐厅（结果：top3如下）"，让模型知道之前做过什么。第二层，关键工具的返回结果不只放消息历史，同时写入 session_state 字典，重建上下文时从 state 读。第三层，做去重检测——工具调用前检查 session_state 里有没有相同参数的历史调用，有就直接复用结果不重复调用。三层加一起基本能解决。
